## Decisions

### Release discovery
Use the fixed GitHub releases/latest API for VonderVuflya/omarchy-zorya-rgb. Accept stable vX.Y.Z tags only, compare numeric versions, ignore draft/prerelease releases and never offer a downgrade just because versions differ. Cache successful checks for six hours and failures for five minutes. Check at widget initialization and every six hours; explicit refresh bypasses cache. Bound the complete HTTP operation to15seconds in a supervised subprocess, including DNS and slow response streaming, and bound response size and reject redirects/unexpected repository URLs. Keep network errors separate from RGB control. Report UI, installed app and running runtime versions separately.

### Explicit update transaction
The native Omarchy updater follows mutable HEAD, so it does not implement the promised exact release update. On user-confirmed update, recheck the proposed tag and clone that exact tag from the fixed repository into staging. Verify manifest identity, tag/version consistency, entry points, source paths, symlink absence, unchanged dependency declarations and Omarchy manifest compatibility before any swap. No pip, package manager, hardware setup, cooling or hardware-service changes occur. Dependency changes require explicit Setup instead.

Serialize updates with a lock and refuse local git edits. Stage on the destination filesystem and rename the full plugin checkout and private application into place with retained backups; support legacy nongit installed plugins too. Plugin backups/failed copies use hidden directory names so Omarchy does not discover duplicate manifest IDs. Restart only zorya-rgb.service, check it is active and verify its reported runtime version with a bounded IPC wait. Roll back both sources and restart the old daemon if installation/health verification fails. Saved state, venv, hardware binaries and configurations remain outside the swapped sources. UI reload happens after the command result has been accepted.

### Error capture and diagnostic report
A successful initial connection is not an unavailable-SDK failure: evaluate connection state after connect returns before retaining any error. Retain one last hardware failure in daemon memory with message, operation, time and bounded traceback; clear current error normally after recovery but keep the last failure available to later UI status requests. Add runtime_version to status for post-update verification. No exception locals or full environment dump. Bound serialized message/traceback evidence to30KiB so escaped Unicode cannot overflow the128KiB status protocol alongside saved state. The UI also retains setup/action/update failures independently of polling and ignores older daemon failure timestamps.

Generate reports only after an explicit user action. Use bounded fixed read-only probes for OS/kernel, plugin/runtime/SDK versions and source commits, PCI/USB models, kernel drivers, I2C access, fixed service states, daemon/device summaries and recognized journal failure counts. Raw logs, serials and full configs are excluded; free text and traceback paths are redacted for credentials, identities and addresses. Privacy filtering is best effort, so always show the report before the user opens the public issue form. Store the full Markdown privately (0700 directory,0600 file), provide copy without a GitHub token, and cap the encoded GitHub draft URL to7500bytes with an explicit truncation notice. When gh is available, a separate Create GitHub issue action submits the complete reviewed report through the user’s existing gh authentication. Bind submission to the SHA256 of the full preview, use a private snapshot, validate the returned fixed-repository issue URL and persist the result/uncertain attempts to prevent accidental duplicate retries. No token is read by Zorya. Without gh/authentication, the user can open the prefilled browser form and perform GitHub’s final Submit or copy the full report. Collection and preview never publish an issue.

### UI and sequencing
Show an accessible up-arrow with target-version tooltip in the panel/widget only when a newer release exists. Opening it presents a version-specific confirmation. Serialize apply with setup/actions/drafts and prevent new edits during update; retain actionable failures. Remove raw JSON Details. Error prompts lead to a human-readable report preview, Open GitHub issue and Copy full report. Browser opening is explicit. Use the Loader item as a dynamic panel reference rather than casting it to the implicit local Panel type: the shell can load equivalent components under distinct qs/file URLs, where the cast returns null and blocks all controls. Existing rounded controls, color dragging, selection and setup/pairing flows remain intact.

### Agent handoff
The copied issue report is a reproducible starting point for Codex: versions, driver/device inventory, operation, error and traceback plus reproduction/expected/actual placeholders. It does not automatically run Codex or apply generated fixes. Investigation and fixes continue through OpenSpec, regression checks, reviewed PR, merged-branch cleanup, tag and release.

## Verification
Use fake GitHub responses, temporary source trees, mocked git/systemd and actual offscreen QML processes. Cover version/cache failures, wrong tags, dirty trees, rollback/health checks, hidden backups, report privacy/URL bounds/clipboard, sticky transient failures and queue/reload races. Live release check is read-only. Never publish test issues or replace hardware services.
