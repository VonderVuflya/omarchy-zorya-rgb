# Lifecycle and permissions

The UI never launches another Quickshell. It sends structured argument arrays to a local CLI; settings travel as JSON rather than shell fragments. The per-user daemon validates updates and writes state atomically.

State is stored under `$XDG_STATE_HOME/zorya-rgb` (normally `~/.local/state/zorya-rgb`). Runtime IPC lives under `$XDG_RUNTIME_DIR/zorya-rgb` with user-only access. Installed tools live under `$XDG_DATA_HOME/omarchy-zorya-rgb`, plugin files under the user Omarchy plugin directory, and services under the user systemd directory.

Sleep detection compares Linux BOOTTIME with MONOTONIC. Wall-clock adjustments and ordinary scheduling delays do not qualify as suspend. Recovery coordinates the managed hardware services, waits for device enumeration, and reapplies the saved scene. It does not periodically restart healthy services.

Installation, migration and uninstallation are explicit operations. Existing unit configuration and enabled/active states are tracked when compatible tools are adopted. Uninstallation stops Zorya-owned units, preserves saved state and restores adopted service state when recorded. It does not uninstall system packages or erase unrelated configurations.

A polkit password may be requested for distribution build packages or narrow hardware access rules. Hardware builders run source compilation as the user. Original system OpenRGB executables and `/usr/share/omarchy` remain unchanged.

Automatic resume lets the compatible Lian Li bridge perform its own re-exec; Zorya must not race that with systemctl stop/restart. OpenRGB starts after USB/I2C settles and an empty startup scan gets one delayed retry. Readiness waiting is bounded so an unavailable controller cannot indefinitely freeze lighting commands to healthy devices. Manual explicitly selected service restarts retain their previous behavior.

SDK connections use a local adapter around the pinned openrgb-python 0.3.6 dependency. Incomplete headers/bodies and EOF close the connection; constructor discovery and each later update share a three-second deadline across nested callbacks. Packet size, controller count, notification depth/count and parser allocation fields are bounded. These guards do not authenticate the loopback server or prevent another local user from occupying a free SDK port. Unsupported/malformed responses fail closed and the existing reconnect path handles the failure.

Discovery exceptions during resume do not bypass the recovery deadline. Explicit hardware setup refuses any discovered full-mode Lian Li service before filesystem or service mutations, including an older Zorya-managed unit. Only recognized RGB-only services can be adopted; existing cooling/LCD control is preserved.

The first-run wizard uses `onboarding plan` for read-only assessment independently of daemon status. Its explicit Start action runs one runtime/hardware/verification stage at a time. Errors remain visible independently of periodic lighting status, and retry reassesses readiness. The runtime-only installer prepares the private SDK and user daemon without adopting hardware or replacing/re-registering the live plugin. Healthy compatible SDK endpoints are reused. Device selection and color application are separate user actions. The distribution's base Python 3.11+ is still required to bootstrap the private environment.

Release discovery contacts only the fixed GitHub latest-release endpoint, with a six-hour success cache, five-minute error backoff and a15-second supervised request deadline. Updates require an explicit confirmed stable tag, retain hidden source backups and touch only the plugin, private app and Zorya user daemon; validation and runtime-version health checks precede completion. No dependency, hardware-service or cooling setup occurs during updates.

Diagnostic reporting is local and explicit. Last worker errors/tracebacks are retained in daemon memory, independent of current error status. Reports use bounded read-only probes and omit raw logs, full configs and device identities. Free text is redacted and previewed; privacy filtering is best effort. Full Markdown is stored in the user's state directory with0600 permissions. Opening a GitHub draft or explicitly submitting through gh is a separate sharing action; no automatic telemetry or issue creation occurs. Full-body SHA256 binding prevents sending a different saved report than the preview. Private submission receipts prevent repeated or uncertain submissions from silently creating duplicate issues.

Explicit runtime setup resolves distribution Python and creates a copied private interpreter, independent of mise's `latest` alias. Rebuilding keeps a backup and restores it if installation fails; an existing Zorya daemon is restarted before subsequent installer steps. Python launchers clear inherited Python overrides, use isolated imports and fall back to distribution Python for diagnosis/Setup if private Python cannot start. Distribution Python ABI removal can still require explicit runtime rebuilding.
